Schedule anything.
Trigger everything.

Cloud Trigger calls the services you already run on a cron, an interval, a calendar rule or an inbound event, and records every result. HTTP, gRPC, GraphQL, Kafka, NATS and AWS targets, workflows with approval gates, and a live dashboard. There is no SDK to add to your code.

Features

One service for every scheduled and event-driven call

Point it at the endpoints you have today. Cloud Trigger owns the timing, retries, chaining and history, so your services stay plain request handlers.

Schedules and events

Every way a job can start, in one place.

  • Cron with time zones, L, # and Jenkins-style H spreading
  • Fixed intervals, one-off runs and RFC 5545 RRULE calendars with excluded dates
  • Start and end bounds, a max run count and jitter on every schedule
  • Chain jobs with after_job; templates read the parent run as {{ parent.* }}
  • Inbound webhooks with HMAC, idempotency keys and rate limits
  • SQS, Kafka and NATS JetStream consumers, deduplicated by delivery id

Targets and connections

Save each service's address and credentials once, then reuse named endpoints.

  • HTTP with response assertions (status, JSONPath, body, latency) and HMAC signing
  • GraphQL, gRPC (inline proto or reflection), SQS, SNS, EventBridge, Kafka and NATS
  • Fan out to several targets, where all or any must succeed
  • Bearer, basic, API-key and OAuth 2.0 client-credentials auth
  • Import endpoints from an OpenAPI 2.0 to 3.2 document, and re-import without losing edits
  • Per-environment overrides, so staging and production can share one deployment

Workflows with approval gates

Build DAGs out of existing jobs or inline steps, and watch them run live.

  • Edges run on success, on failure or on any outcome
  • Approval gates with timeouts, decided in the UI, the API or by an AI agent
  • Optional schedules, so a whole pipeline can run nightly
  • Every step is a normal run, with history, retries and replay

See what failed, and fix it

Every attempt is recorded with its request, response and error.

  • A failed-runs inbox with bulk replay and dismiss
  • A "Why didn't it run?" explainer for each job
  • Dashboard of outcomes, p50/p95 latency, late runs and top errors
  • Notifications to webhooks, Slack and email, delivered through a retried outbox

Reliability

Built to run more than one replica

Schedulers and workers coordinate through the database, so you can scale either without a separate queue or lock service.

Exactly-once firing

Each fire time has an idempotency key backed by a unique index, so it never runs twice.

Leases and a reaper

Workers hold renewable leases. If a worker dies, its runs are requeued.

Overlap policies

Allow, forbid, replace or buffer one, per job or per group.

Missed runs

Skip, run once or run all after downtime, within a grace window you set.

Retries and auto-pause

Fixed or exponential backoff, timeouts, and a pause after N failures in a row.

SLAs

Flag runs and jobs as late on start delay, duration or time since last success.

Rate limits

Per-second and max-concurrency limits for a group, enforced across replicas.

Backfill

Enqueue past fire times idempotently, with a dry run that lists them first.

Config as code

Jobs are plain YAML

Export every job, keep it in git, and import it into another deployment. Jobs refer to connections by key, and secrets are redacted on the way out.

The same API is open to scripts, CI and AI agents.

  • REST API with OpenAPI docs at /docs
  • An MCP server at /mcp for agents
  • Live run updates over server-sent events
name: Nightly invoice run
tags: [billing]
trigger:
  type: cron
  config:
    expression: H 2 * * *
    timezone: Europe/Berlin
target:
  type: http
  connection: { key: storefront, endpoint: charge }
  config:
    assertions:
      expectedStatus: [2xx]
policy:
  retry: { maxAttempts: 5, backoff: exponential }
  overlap: forbid
  sla: { maxDurationMs: 600000 }
notifications:
  - on: [permanent_failure, late]
    notifier:
      type: webhook
      config: { url: https://hooks.example.com/oncall }
# Start a run from any system that can send a POST
curl -X POST https://ct.example.com/hooks/$JOB_ID/$TOKEN \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: order-1001' \
  -d '{"type":"order.paid","order":"A-1001"}'

# The job's template reads it as {{ event.body.order }}
# Run a job now; retries with the same key run once
curl -X POST https://ct.example.com/api/jobs/$JOB_ID/run \
  -H "x-api-key: $CT_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"idempotencyKey":"deploy-4821"}'

# Export every job as YAML
curl https://ct.example.com/api/jobs/export \
  -H "x-api-key: $CT_API_KEY" > jobs.yaml
# Give an AI agent the same API, with the same scopes
claude mcp add --transport http cloud-trigger \
  https://ct.example.com/mcp \
  --header "x-api-key: $CT_API_KEY"

Operations

Ready for production on day one

Sign-in and access

Password accounts (argon2), OIDC with PKCE and hashed API keys, with read, write and admin scopes. Optional anonymous read access for wallboards.

Secrets at rest

Secret fields are encrypted with AES-256-GCM, shown as *** in every response, and can be rotated. Reference shared secrets as {{secret:NAME}}.

Observability

OpenTelemetry spans per attempt with traceparent forwarded, Prometheus /metrics, status badges and an iCal feed of upcoming runs.

A good fit when

  • Your work already sits behind HTTP, gRPC or a queue, and you want to call it on a schedule
  • You want cron and event triggers, retries, history and alerts in one place instead of scattered crontabs
  • You need to run it yourself, on Postgres, MongoDB or a single SQLite file
  • Several teams or environments share one scheduler

Look elsewhere when

  • You want durable, step-by-step functions written inside your code; an SDK workflow engine suits that better
  • You need a hosted service and don't want to run anything
  • You need sub-second scheduling precision

Quick start

Deploy anywhere

Docker Compose

Everything in one container, with MongoDB and a demo echo target.

git clone https://github.com/dragonxsx/cloud-trigger
cd cloud-trigger
docker compose -f deploy/docker-compose.yml \
  --profile app up --build

Open localhost:8080 and enter the setup token local-setup-token.

Kubernetes

Separate API, scheduler and worker Deployments, with an HPA on workers.

helm install ct deploy/helm/cloud-trigger \
  --set secrets.values.MONGO_URI=… \
  --set secrets.values.SETUP_TOKEN=… \
  --set secrets.values.DATA_ENCRYPTION_KEY=…

Demo with sample data

A SQLite server seeded with jobs, failures and a workflow waiting for approval.

pnpm install && pnpm build
pnpm --filter @cloud-trigger/demo start

Sign in as demo / demo-password.
